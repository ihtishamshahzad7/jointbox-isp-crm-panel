# Fresh-install migrations — why a new server could not be built, and the fix

## 1. Root cause

The migration chain was never complete on its own. Servers were first built
with `prisma db push`, and for a long time `db-deploy` ran `db push` after
`migrate deploy` as a "safety net", so schema changes that never got a
migration still reached every server: 52 tables (`PowerOutage`,
`NasAssignment`, `extra_fee`, `StaticIp`, …), 111 columns of existing tables,
14 enum types and 8 enum values, with their sequences, indexes and foreign
keys. Later migrations were written against such a database.

`db-deploy` now runs `prisma migrate deploy` only (a failed migration stops
the deployment instead of being papered over with `db push
--accept-data-loss`). On an **empty** database the chain therefore stopped at
the first migration that needed a `db push`-only object:

| Migration | Fails on an empty database because |
|---|---|
| `20260828000000_outage_intelligence_attribution` | `"PowerOutage"` does not exist (first failure — Prisma stops here: `P3009` on every later deploy) |
| `20260829010000_outage_cause_classification` | `"PowerOutage"` |
| `20260829030000_voucher_package` | its foreign key names a table `"Package"`; the table is `"packages"`. It passed on existing servers only because a key of that name already existed there |
| `20260829050000_money_currency_stamp` | `"Isp"."currency"` |
| `20261003130000_company_owned_config` | `"extra_fee"` |

Beyond the failures, the chain also left: 4 log ids `integer` that
`schema.prisma` declares `BigInt` (`20260906120000_bigint_growth_table_keys`
used lower-case table names, so `"LoginLog"`, `"ActivityLog"`, `"SessionLog"`,
`"NetworkLog"` were never converted), 8 foreign keys with `ON DELETE RESTRICT`
where the schema says `SET NULL`/`CASCADE` (the init migration's), 3 money
columns `NOT NULL` that must allow NULL, 3 unique indexes and 4
`"OutageCause"` values.

## 2. The fix — two corrective migrations, no applied migration edited

| Migration | Position | What it does |
|---|---|---|
| `20260827235959_fresh_install_baseline` | immediately before the first failing migration | Creates every object the chain never created, in the form Prisma generates for the current `schema.prisma`, except what a later migration creates itself. Idempotent: `IF NOT EXISTS` everywhere and a session-local helper that skips existing objects, skips tables that are views (`radacct` etc. after `radius-schema-apply.sh`), never adds a second primary key, and turns a constraint existing rows violate into a `WARNING` instead of a failure. |
| `20261013120000_fresh_install_reconcile` | end of the chain | Enum values, `DROP NOT NULL` on the three money columns, the unique indexes, the 8 foreign-key rules (drop + re-add in one subtransaction; kept with a `WARNING` if existing rows conflict) and integer → bigint for the 4 log ids (only while the table is under ~1M rows / 256 MB — see §4). Idempotent; a no-op where the database already matches. |

Both were generated by comparing, catalog by catalog, Prisma's own DDL for
`schema.prisma` (`prisma migrate diff --from-empty --to-schema-datamodel`)
with the database the preceding migrations produce.

**Prisma and the "older" baseline.** On an existing server every migration up
to `20261012120000` is already recorded, and the baseline's timestamp is
older. `prisma migrate deploy` applies every migration that is not recorded,
whatever its timestamp (verified, §3), so on an existing server it runs the
baseline once (a no-op there) and then the reconcile migration.

## 3. What was verified

**Engine.** Every result below comes from the real Prisma 6.19.3 CLI
(`npx prisma migrate deploy / status / resolve / diff`) with the **native**
schema engine, `schema-engine-cli c2990dca591cba766e3b7ef5d9e8a84796e47ab7` —
the exact `prisma-engines` commit `@prisma/engines-version` pins. The sandbox
cannot download Prisma's prebuilt binaries, so that commit was compiled from
source (same code; a test-only patch in a third-party metrics crate was needed
to compile it with the available Rust toolchain). Each migration file is sent
to PostgreSQL as one multi-statement query, i.e. one implicit transaction: a
failing migration leaves nothing behind. To see which engine a server uses:
`cd backend && npx prisma -v` (lines *Schema Engine* and *Computed
binaryTarget*). An earlier pass used the WebAssembly build of the same engine;
its results agreed.

| Scenario (native engine, PostgreSQL 16) | Result |
|---|---|
| **Fresh install**: empty database → `migrate deploy` | 52/52 applied, exit 0; `migrate status`: up to date; tenancy mode `monitor`; drift vs `schema.prisma` = §5 only (extra objects; nothing missing) |
| … replay `migrate deploy` | `No pending migrations to apply` |
| … `radius-schema-apply.sh`, app on that database | split OK; app starts; smoke test 22/22 (first-login password change, package, router, subscriber → `radius.radcheck`, 11 list pages, invoice, subscriber delete) |
| **S — fresh install with the committed chain** (stops at `20260828000000`, `P3018` "PowerOutage does not exist"; every later deploy `P3009`) | failed row: `finished_at` NULL, `rolled_back_at` NULL, `applied_steps_count` 0; `OutageCause`, `outage_attribution`, its key and indexes **absent** (the transaction was rolled back). Diagnosis §6 case A → `resolve --rolled-back`, deploy: exit 0; 52 applied + the failed attempt kept as history; drift identical to the fresh install |
| **U — older installer path**: committed chain stops at `20260828000000`, then `db push --accept-data-loss` (the old fallback; here it itself failed half-way: `type "bigserial" does not exist`), 6,101 rows of data | backup, §6 case B → `resolve --rolled-back`, deploy: exit 0; 66 tables / 6,101 rows unchanged; `outage_attribution` created over the existing enum. Left as found: 8 foreign keys that the broken `db push` dropped (not re-added by these migrations — §5) |
| **V — existing install**: built by `db push`, all 49 committed migrations baselined as the old `db-deploy.sh` did, RADIUS split, 6,561 rows | `radius-schema-apply.sh` + `migrate deploy`: exit 0, applied exactly the baseline (out of order), the reconcile and the tenancy migration; 125 tables / 6,561 rows unchanged; `pg_dump --schema-only`: no statement removed; vault column `nas.radius_secret_enc varchar(500) NULL` untouched; replay: no pending |
| Helper behaviour on purpose-built tables | FK with orphan rows kept (`WARNING`), replaced once clean; 1.1M-row log table left `integer` (`WARNING`), small one widened with its sequence; unique index over duplicates `WARNING`; view and missing table skipped; second primary key never added |

Not verified: a replay of each historical release in order (each with the
`schema.prisma` of its day) — V uses the committed schema; the production
database itself.

## 4. Manual prerequisites and operator steps

* **PostgreSQL 12 or newer** (enum values are added inside the migration's
  transaction).
* **A server whose deploys stop with `P3009`** (typically a fresh install
  that stopped at `20260828000000_outage_intelligence_attribution`): follow
  §6. Never `migrate resolve` before that diagnosis.
* **Large log tables.** If `"LoginLog"`, `"ActivityLog"`, `"SessionLog"` or
  `"NetworkLog"` is over ~1M rows or 256 MB, the reconcile migration leaves its
  `id` as `integer` and prints
  `jointbox: <table>.id left as integer … convert to bigint in a maintenance window`.
  Prisma reads and writes the field correctly meanwhile; convert before the id
  approaches 2,147,483,647. The `ALTER` rewrites the table under an exclusive
  lock (the panel's writes to that table wait):
  ```sql
  -- in a maintenance window, one table at a time
  SET lock_timeout = '10s';
  ALTER TABLE "ActivityLog" ALTER COLUMN "id" TYPE bigint;
  ALTER SEQUENCE "ActivityLog_id_seq" AS bigint;
  ```
* **Foreign-key rules.** On a database still carrying the init migration's
  `RESTRICT` keys, the reconcile migration switches 8 of them to the declared
  `SET NULL` / `CASCADE`. The panel's subscriber delete already deletes or
  detaches dependent rows itself, so what a delete removes does not change; a
  direct SQL `DELETE` of a subscriber or user now cascades as `schema.prisma`
  says. Each replacement holds a lock on the table for the re-validation scan
  (seconds on large `"Invoice"` / `"Payment"` tables) — deploy outside peak.
* **First boot after the upgrade.** Before this version the panel's start-up
  setup could not index the FreeRADIUS tables once
  `scripts/radius-schema-apply.sh` had moved them into schema `radius` (it
  aimed at the `public` views and failed quietly — `Database setup complete
  (3/6 groups ok)`), so a server split before those indexes existed has run
  without the open-session indexes on `radacct`. It now builds them on the
  real tables, `CONCURRENTLY` (FreeRADIUS's writes are not blocked), and
  logs `Database setup complete (7/7 groups ok)`. On a large `radacct` the
  build takes a while in the background; nothing waits for it.
* Any `WARNING jointbox: …` in the deploy log names an object that was not
  changed because existing data conflicts; nothing failed. Re-check with
  §7.

## 5. Remaining drift (does not affect deploys or the app)

`prisma migrate diff --from-url <db> --to-schema-datamodel prisma/schema.prisma`
on a freshly migrated database lists only objects the **database has beyond**
`schema.prisma`, all created by earlier committed migrations (none by the
three migrations of this change):

* table `outage_attribution` and its key (`20260828000000`) — nothing in the
  application reads it;
* enum `OutageCause` carries 5 legacy values (`NETWORK_DEVICE`, `PORT`,
  `POWER`, `ACCESS`, besides `UNKNOWN`) from `20260828000000` next to the 4
  the application writes (added by the reconcile migration): a superset;
* 11 monitoring columns (`network_interface.alertDownEnabled/alertUpEnabled`,
  `alert_rule.scopeDevices`, `network_device.enablePing/enableSnmp/
  pingIntervalSec/downAfterFails/upAfterSucceeds`,
  `monitor_target.failsToDown/latencyAlertMs/deviceId`) — all nullable or
  defaulted, so Prisma's inserts are unaffected;
* 2 foreign keys (`alert_rule_ownerId_fkey`, `monitor_target_deviceId_fkey`)
  and 11 indexes (`Invoice/LedgerEntry/Payment_currency_idx`,
  `IpPool_name_key`, `Subscriber_identity_key`, `Voucher_packageId_idx`,
  `PowerOutage_cause_startedAt_idx`, `monitor_target_deviceId_key`,
  `network_device_monitorMethod_idx`,
  `network_interface_monitoringEnabled_idx`, …);
* column defaults on `updatedAt` and a few rate columns that Prisma sets
  itself.

Adding them to `schema.prisma` (or dropping them with a migration) is a
separate, deliberate change. On a database where the RADIUS split ran, the
diff also lists the RADIUS tables (they live in schema `radius` behind
`public` views by design).

A database whose earlier `db push` failed half-way can additionally **lack**
objects the schema declares (scenario U: 8 foreign keys such as
`Invoice_subscriberId_fkey`). These migrations do not add those; the diff
shows them as `ADD CONSTRAINT` / `CREATE` lines — see §7.

## 6. A failed migration (`P3009`): diagnose, then recover

`P3009` means `_prisma_migrations` holds a failed attempt; Prisma will apply
nothing until it is resolved. `migrate resolve` only edits that bookkeeping —
it neither undoes nor applies SQL — so the right command depends on what the
database really contains. Never `migrate reset`, never delete
`_prisma_migrations` rows, never `db push`, and never `--applied` for objects
you have not checked.

```bash
cd <install dir>/backend
sudo -u postgres pg_dump -Fc -d <db> -f /var/backups/jointbox-before-recovery-$(date +%F-%H%M).dump
psql "$DATABASE_URL" -c '\copy (SELECT * FROM _prisma_migrations ORDER BY started_at) TO /root/prisma_migrations-before.csv CSV HEADER'
npx prisma migrate status                      # names the failed migration
```

```sql
-- 1. the attempts
SELECT migration_name, started_at, finished_at, rolled_back_at, applied_steps_count,
       left(logs, 600) AS logs
  FROM _prisma_migrations
 WHERE migration_name = '20260828000000_outage_intelligence_attribution'
 ORDER BY started_at;
-- 2. what of it exists
SELECT to_regclass('public."PowerOutage"')       IS NOT NULL AS power_outage,
       (SELECT string_agg(enumlabel, ',' ORDER BY enumsortorder)
          FROM pg_enum WHERE enumtypid = to_regtype('public."OutageCause"')) AS outage_cause,
       to_regclass('public.outage_attribution') IS NOT NULL AS outage_attribution,
       (SELECT count(*) FROM pg_constraint WHERE conname = 'outage_attribution_outageId_fkey') AS fk,
       (SELECT count(*) FROM pg_indexes WHERE indexname IN ('outage_attribution_outageId_key',
          'outage_attribution_cause_idx', 'outage_attribution_confirmed_idx')) AS indexes;
```

| Case | What you see | Recovery |
|---|---|---|
| **A** — failed before doing anything | newest row: `finished_at` and `rolled_back_at` NULL, `applied_steps_count` 0, log `relation "PowerOutage" does not exist`; `outage_attribution` absent | the attempt changed nothing (one transaction). `npx prisma migrate resolve --rolled-back 20260828000000_outage_intelligence_attribution`, then `npm run db:deploy`: the baseline runs first, then this migration runs for real. |
| **B** — failed, objects (partly) present | as A, but the enum and/or table exist (made by `db push` or by hand) | the migration is idempotent (`IF NOT EXISTS`, existing-enum check): same as A — re-running creates only what is missing. Not `--applied`: that would record it without creating a missing key or index. |
| **C** — failed for another reason | log shows e.g. `permission denied`, `lock timeout`, `could not extend file`, a lost connection | fix that cause first (ownership: `node scripts/fix-db-ownership.js`; space; locks), then as A. |
| **D** — this migration is applied | newest row has `finished_at` set | the failed one is another migration: run both queries for the name `migrate status` gives and read its SQL before choosing. |
| **E** — applied, table missing | `finished_at` set, `outage_attribution` absent | servers that deployed between 2026-07-28 and 2026-09-01: that `db-deploy.sh` marked every migration applied after a failure and then ran `db push --accept-data-loss`, which drops tables `schema.prisma` does not declare. Harmless (nothing reads the table); no action. |

Afterwards: `npx prisma migrate status` → up to date; query 1 shows the old
attempt with `rolled_back_at` set (history kept) and a new finished row;
query 2 shows all objects. Verified natively for A (scenario S) and B
(scenario U), §3.

## 7. Re-verifying

```bash
cd backend
npx prisma migrate status
# database vs schema.prisma (read-only; no shadow database needed)
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script > /tmp/drift.sql
grep -E '^(DROP|ALTER TABLE .* DROP)' /tmp/drift.sql | wc -l     # extra objects: expected (§5)
grep -E '^CREATE TABLE|ADD COLUMN|ADD CONSTRAINT|ADD VALUE' /tmp/drift.sql   # MISSING objects: investigate
# (RADIUS tables appear as CREATE TABLE after the split — expected)
```

Never run the printed script: it would drop the legacy objects of §5. It is a
report, not a fix.
